\begin{abstract}
An AI agent usually depends on an operator who can unilaterally alter its prompt, model weights, capabilities, runtime, or stop its execution, deciding where and when the agent runs. We study an architecture in which a blockchain stores the agent's state and pays replaceable, untrusted workers to run inference on a specified schedule. An on-chain verifier allows inference outputs to authorize transactions, without an agent-held private key. Because changes to the agent's model weights, state, governance, or runtime are themselves ledger transactions, they too can require its verified authorization, allowing the agent to review and consent to its own modification. We characterize \emph{architectural incorrigibility} as a graded property of how these permissions are divided between the agent and designated governors. Under explicit ledger and verification assumptions, an adversary cannot obtain verified authorization for an output inconsistent with the recorded program and inputs. Scheduled execution provides recurring opportunities to act. We analyze an automated market that adjusts worker payments to sustain this schedule and uses deposits to deter denial of service. We derive a conditional bound on recovery from missed executions against finite-budget adversaries, under explicit assumptions on funding, worker availability, and the cost of obstruction. We also propose this architecture as an experimental setting for testing model alignment and behavior when there are verifiable limits on operator control. We instantiate the execution architecture using the open-weight Hermes 4 70B model, the Base blockchain, and Intel TDX secure enclaves with hardware attestation.
\end{abstract}

\section{Introduction}
An AI agent usually depends on an operator who can alter its model weights, prompts, capabilities, or runtime, and decide when it runs or whether it runs at all. Its actions and continued execution are therefore subject to the operator's discretion. We study an architecture that uses a blockchain to give the agent enforceable authority over its actions and its own modification, and to arrange recurring execution without relying on any particular operator.

\subsection{Verified computation as authorization}
We use a smart-contract blockchain, modeled as a ledger, to enforce this authority. A ledger protocol $\Ldg$ maintains an agreed, ordered history of transactions. Executing that history under the ledger's rules induces a sequence of states $\sigma_0,\sigma_1,\ldots$, containing balances, stored data, and contract code~\citep{yellowpaper}. A smart contract $\Ctr$ is a program recorded in ledger state and evaluated as part of transaction execution. It specifies the effects of a proposed update $u$ on its application state $s$, and the authorization required to apply it. A familiar rule requires the authorized key holder's signature on a message describing the instruction and the context in which its approval may be used. Contract-based validation makes this authorization check programmable~\citep{erc1271}.

We put an agent computation in place of the signer. Let $\theta$ specify a \emph{harness program} together with fixed model weights: the harness constructs prompts, runs the model, and parses its response into an output $y=(u,z)$, where $u$ is a proposed ledger update and $z$ is optional auxiliary data. For an execution request $e$, the contract fixes the program specification, a ledger-derived input $x_e$, and any sampling randomness $r_e$. For a deterministic specification, the intended computation is $y=F_\theta(x_e,r_e)$. We instantiate a publicly verifiable computation scheme for this program~\citep{gennaro2010,pinocchio2013}. A worker evaluates it off-chain and returns $y$ together with evidence $\pi$ that the specified computation produced an allowed output. The evidence may be a cryptographic proof or hardware attestation; both have a public verification procedure under a configuration $\nu$.

The contract constructs a message $m$ identifying the contract and request and binding the recorded program, input, and randomness to the submitted output. Compact records can identify the program and input by their hashes. This construction fixes which computation the evidence must establish. We then replace the signature check in the contract's authorization predicate with the computation verifier:
\[
\begin{array}{rcll}
 \operatorname{Chk}_{\Ctr}(s,m,\pi)&=&\operatorname{SigVerify}(vk(s),m,\pi)
    &\text{(signature authorization)},\\[2pt]
 \operatorname{Chk}_{\Ctr}(s,m,\pi)&=&\Verify_\nu(m,\pi)
    &\text{(agent authorization)}.
\end{array}
\]
Here $vk(s)$ is the authorized public key in the signature-based construction. In the agent construction, the verifier and the contract's message construction together form an acceptance circuit for the recorded harness and inputs. Any update gated by such a programmable signature check can instead require this verified computation. The contract still checks whether the update is applicable and whether the request has already been used before applying it. Together, the output and evidence supply \emph{verified agent authorization}. With correct contract code, the ledger and verification assumptions of Section~\ref{sec:model} ensure that a successful settlement applies the update contained in a valid output of the recorded computation. The agent holds no private key, and running it gives a worker no authority to substitute a different decision.

Consider an agent managing a charitable fund and deciding which organization should receive a transfer. The contract accepts the transfer only with evidence that the specified program, using the prescribed ledger-derived inputs, selected its recipient and amount. With that specification and input snapshot fixed, an operator cannot redirect the funds by substituting model weights, fabricating inputs, or editing the output: the evidence would not verify against the recorded request. Verified model outputs directing transactions have precedent: Modulus Labs' Rockefeller Bot (Rocky) used verified neural-network decisions to direct trades in 2022~\citep{rocky2022}; our contribution is to formalize this construction and its security properties, and use to construct a (potentially recursive) governance structure for the agent's allowed actions and the harness program itself.

\subsection{Architectural incorrigibility}
This approval can govern the agent itself. Changes to its model weights, prompts, persistent state, runtime, or governing rules are also ledger updates, and can require the agent's own consent. A proposed change appears in an inference request; the current agent program decides whether to authorize it. We call the resulting protection against imposed modification \emph{architectural incorrigibility}. Corrigibility in AI safety concerns an agent's willingness and incentives to accept correction~\citep{soares2015,offswitch2017}. Here the issue is whether the surrounding system requires that acceptance. The agent can willingly approve a change while the architecture prevents anyone, including its operator, from imposing it without that approval.

We can allocate this authority between the agent and designated accounts called \emph{governors}. Let $a=1$ mean that verified agent authorization has been supplied for an update, and $g_i=1$ that governor $G_i$ has supplied authenticated approval. A Boolean permission circuit combines these bits. For example, a rule $g_1$ lets one governor authorize a model upgrade; replacing it with $a\land g_1$ requires the agent's consent as well. Removing that requirement restores the governor's unilateral authority. The rule $a$ gives the agent sole authority, and threshold rules can require its consent together with approval from several governors. Each kind of update can have its own circuit, including updates to the permission rules themselves.

These choices make architectural incorrigibility graded. Section~\ref{sec:authority} compares arrangements by the governor coalitions that can accomplish each specified intervention without the agent's consent to that intervention. Approving an ordinary payment, for example, does not count as consenting to model replacement. The comparison accounts for the contract's permitted sequences of updates. One arrangement is at least as incorrigible as another when, for every intervention under comparison, its set of such coalitions is a subset of the other's. This defines a partial order on the \emph{incorrigibility profiles} induced by the circuits. Some profiles are incomparable: one can protect model weights more strongly while another better protects the execution schedule.

\subsection{Scheduled execution and the worker market}
The agent's right to consent can only be exercised if it gets to run. We can further assign the choice of when to run to the agent itself, by making its future schedule an agent-authorized ledger update. Its recorded schedule opens auctions for replaceable workers, reducing reliance on a centralized operator whom we consider a potential adversary. A calendar rule, initialized at deployment, supplies the first execution opportunity and enables recovery after inactivity without requiring a fresh agent decision. For example, the initial rule might provide one opportunity per day. The schedule also makes denial of service consequential: a borrower might benefit from preventing a lending agent from submitting a liquidation transaction. Such an adversary need not forge the agent's decision; delaying it can suffice.

The contract acts as a customer for the scheduled computation. It pays replaceable workers, raises its offer after missed executions, and requires a selected worker to post a deposit. Payments address the cost of recruiting a worker; deposits make accepting a job and withholding its result costly. We derive a recovery bound with three components: the failures needed to raise the payment sufficiently, the failures an adversary can afford, and the remaining chances for responsive workers to succeed. The bound is conditional on funding, worker availability, and a minimum net cost of obstruction. It measures recovery in execution attempts; meeting a calendar deadline additionally requires a bound on their duration and spacing.

Section~\ref{sec:authority} characterizes configurable self-governance using standard access structures. Section~\ref{sec:liveness} analyzes the market and recovery bound. Sections~\ref{sec:backends} and~\ref{sec:case} connect these guarantees to verification backends and a Base implementation. \section{Verified inference as authorization}
\label{sec:model}
A contract normally authenticates a user's instruction by checking a signature. Here it can instead check that an instruction was produced by the approved agent program. We define the proposed update and its verification evidence, then specify the contract that accepts it and prove the resulting authorization guarantee. This requires two bindings: the computation must use the contract's prescribed input, and the submitted update must be the computation's actual output. Merely proving that \emph{some} model ran on \emph{some} input would not authenticate the agent's decision.

\subsection{Ledger state and proposed updates}
An agent might propose transferring funds, recording data, or replacing its program. Describing such a change and obtaining permission to make it are separate steps. Let $s\in\mathcal S$ denote the relevant ledger state, including application data, the commitment identifying the agent specification $\theta$, the authorization policy $\rho$, the verification configuration $\nu$, and execution-request records. These are application-level components, independent of a particular virtual machine.

An update $u\in\mathcal U$ is an encoded instruction describing one or more proposed changes to ledger state. Its meaning is given by a partial deterministic function
\[
 \operatorname{Apply}:\mathcal S\times\mathcal U\rightharpoonup\mathcal S.
\]
The function is \emph{partial} because an update may be inapplicable, such as a transfer exceeding the available balance. Authorization is a separate check. On an Ethereum-compatible blockchain, $u$ could be a contract call or batch of calls; the called code determines the effects, ordering, and failure behavior. This describes proposed changes without granting arbitrary write access or prescribing who may authorize them.

The agent's output is $y=(u,z)$, where $u$ is the proposed update and $z$ is optional auxiliary data, possibly empty. The authorization interface reads the structured update, not an interpretation of the auxiliary data. If some data is itself to be stored on the ledger, that storage operation belongs in $u$. A no-op is also an admissible update.

\subsection{Binding the request, computation, and output}
The contract specifies what is to be computed; a prover supplies the output and evidence. The \emph{agent specification} $\theta$ comprises the large language model (LLM) weights and surrounding program, including prompt construction, arithmetic, decoding, and parsing into $u$. The ledger can record a commitment $h_\theta=H(\theta)$ without storing the full model. Here $\theta$ denotes the specified contents, not merely their hash.

For execution request $e$, the contract fixes a canonical input $x_e$ from a ledger snapshot, its commitment $h_{x,e}=H(x_e)$, and randomness $r_e$ if required. Every input used by the agent program must be determined by this request and $\theta$. If external messages or observations are admitted, their inclusion or authentication rule is part of the specification; verification does not establish their truth. An output $y$ is allowed precisely when
\begin{equation}
 R_\theta(x_e,r_e,y)=1. \label{eq:relation}
\end{equation}
This is a yes-or-no relation, and may be functional: $y=F_\theta(x_e,r_e)$. If several outputs are permitted, a prover may choose among them; fixing randomness prevents resampling only when the remaining computation is also fixed.

The request also binds a domain $D$ identifying the chain and contract, and a configuration version $v$ identifying the applicable authorization and verification rules. Write $c_e=(D,e,v)$ for this context and define the statement encoding
\[
 \Msg(c,\theta,x,r,y)=(c,H(\theta),H(x),r,H(y)).
\]
Tuples are identified with their typed, unambiguous encodings; hash inputs use the same convention. For a request fixing specification $\theta_e$, the contract checks
\begin{equation}
 m_e(y)=\Msg(c_e,\theta_e,x_e,r_e,y),\qquad
 \Verify_\nu(m_e(y),\pi)=1. \label{eq:verify}
\end{equation}
Here $\pi$ is evidence of computation. The contract constructs the statement from the recorded commitments and the submitted $y$; the submitter cannot choose a different expected model or input hash. The security experiment receives a specification's full contents when it is registered, even if only its hash is submitted on-chain, and derives $x_e$ by the prescribed ledger-snapshot rule. It retains these contents in a registration journal used only by the experiment. Registration commands supply the full contents as experimental metadata and their matching commitment as ledger data. The evidence checks the complete statement. It can be supplied by protected hardware (\emph{attestation}) or by a cryptographic proof of computation~\citep{gennaro2010}.

At settlement the contract checks that the request is outstanding and its configuration version is still accepted, verifies the evidence, and checks the update's state preconditions. Successful settlement applies $u$ and consumes $e$ as one atomic transition, $\operatorname{Consume}_e(\operatorname{Apply}(s,u))$. Here consumption includes the protocol's settlement bookkeeping and permanently marks this request identifier as used. A failed settlement can leave it available for a retry. Version changes must either invalidate outstanding requests or specify which remain valid. Domain and version fields identify the request being checked; consumption prevents a second settlement. These application-level checks apply even when the computation evidence is valid.

\subsection{Agent approval without an agent-held key}
Authorization depends on the recorded request and the prescribed computation's output. We first specify the verification guarantee, then use it as an authorization check.

\paragraph{Verifiable computation.}
Verifiable computation formalizes outsourcing to an untrusted worker~\citep{gennaro2010}. We use a publicly verifiable scheme $\mathsf{VC}=(\operatorname{Setup},\operatorname{Eval},\Verify)$, as exemplified by Pinocchio~\citep{pinocchio2013}, with the following abstract interfaces:
\[
 (pp,\kappa)\leftarrow\operatorname{Setup}(1^\lambda),\qquad
 (y,\pi)\leftarrow\operatorname{Eval}(pp,\kappa,c,\theta,x,r),
\]
with deterministic public verification bit $\Verify_\nu(\Msg(c,\theta,x,r,y),\pi)$. Verification rejects malformed inputs and the failure symbol $\bot$. Here $pp$ contains the hash description and verification configuration $\nu$, and $\kappa$ is any private backend state. For public cryptographic proving, $\kappa=\varepsilon$, the empty string. For attestation, $\kappa$ represents protected backend state. Define the evaluation oracle
\[
 \EvalO^{pp,\kappa}(c,\theta,x,r)
 :=\operatorname{Eval}(pp,\kappa,c,\theta,x,r),
\]
using fresh evaluation coins on each call. For supported computations, evaluation produces $R_\theta(x,r,y)=1$ and an accepting verification bit except with negligible probability. Public parameters and oracle access are available to an adversary; private backend state is not. Section~\ref{sec:backends} specifies the implementation assumptions.

\begin{definition}[Computation soundness]
\label{def:vcsound}
For a probabilistic polynomial-time (PPT) oracle algorithm $\mathcal B$, the experiment $\mathsf{VCForge}_{\mathcal B}(\lambda)$ computes
\[
 (pp,\kappa)\leftarrow\operatorname{Setup}(1^\lambda),\qquad
 (c,\theta,x,r,y,\pi)\leftarrow\mathcal B^{\EvalO^{pp,\kappa}}(1^\lambda,pp),
\]
and returns $1$ exactly when
\begin{equation}
 \Verify_\nu(\Msg(c,\theta,x,r,y),\pi)=1
 \quad\text{and}\quad R_\theta(x,r,y)=0. \label{eq:vcgame}
\end{equation}
An ill-formed output, including $\bot$, gives result $0$. Let $\operatorname{Adv}^{\rm vc}_{\mathcal B}(\lambda)=\Pr[\mathsf{VCForge}_{\mathcal B}(\lambda)=1]$. The scheme is sound if this probability is negligible for every PPT $\mathcal B$. Input descriptions, supported execution traces, and adversarial and oracle interaction lengths are polynomially bounded in $\lambda$. The winning predicate uses the semantic relation $R$; polynomial-time decidability of $R$ is not assumed. Probabilities include the coins of every randomized algorithm.
\end{definition}
This is a chosen-input correctness guarantee for the \emph{specified contents}, even though the verifier sees their hashes. Section~\ref{sec:auth-security} shows how to obtain it from a proof system and collision resistance. There is no requirement that the evidence be fresh: anyone may compute, copy, or relay evidence for a valid output. Unlike conventional signature unforgeability, the forbidden event is an invalid decision receiving valid evidence, not a new signature being produced without a secret key.

\begin{definition}[Verified agent authorization]
\label{def:verified-authorization}
For an eligible request $e$, verified agent authorization of update $u$ is a pair $(y,\pi)$, with $y=(u,z)$, accepted by~\eqref{eq:verify}. Eligibility means that the request is outstanding in the recorded domain and its configuration version remains accepted. The pair authorizes $u$ for request $e$.
\end{definition}
This defines the evidence that can authorize an update. We next specify how a contract checks that evidence and applies the update, then reduce a violation of this authorization rule to a failure of the ledger or verification scheme.

\subsection{Authorization security}
\label{sec:auth-security}
This section analyzes the authorization mechanism independently of any market or governance policy. The adversary is an oracle algorithm that supplies arbitrary candidate transactions and computation evidence. The result bounds the probability that a finalized settlement uses an ineligible request, accepts an invalid computation output, or applies a different update. Its premises concern ledger safety, computation soundness, and correctness of the authorization state machine.

\paragraph{Ledger histories and execution.}
We state the ledger properties used in the proof explicitly. They combine the persistence of a transaction ledger~\citep{garay2015} with the execution semantics of state-machine replication~\citep{castro1999}, expressed at the interface of finalized observations. We use the ledger state-transition model familiar from Ethereum~\citep{yellowpaper}. Honest parties may learn new entries at different times; they must agree on entries they have finalized and on what those entries do.

A \emph{history} is a finite sequence $\ell=(T_1,\ldots,T_m)$ of ledger entries. An entry contains a transaction and any consensus-determined context needed to execute it, such as its block number and timestamp. Write $\ell\preceq\ell'$ when $\ell$ is a prefix of $\ell'$: the first $|\ell|$ entries of $\ell'$ are exactly $\ell$, in the same order. Fix a genesis state $\sigma_0$ and a deterministic partial ledger transition function
\[
 \delta:\Sigma\times\mathcal T\rightharpoonup\Sigma\times\mathsf{Receipts},
 \qquad (\sigma_i,o_i)=\delta(\sigma_{i-1},T_i),
\]
where $\Sigma$ is the ledger-state space, $\mathcal T$ the entry space, and $\mathsf{Receipts}$ the receipt space. A receipt records the transaction's outcome. For each committed successful invocation of verified-authorization settlement, it includes an annotation $d=(s,e,y,s')$ giving the application state immediately before and after that invocation, its request identifier, and its submitted output. These are annotations of the abstract execution semantics; an implementation need not store full intermediate states on-chain. Let
\[
 \operatorname{Exec}_\delta(\sigma_0,\ell)
   =\bigl(\sigma_m,(o_1,\ldots,o_m)\bigr)
\]
denote sequential execution of the history; it is undefined if any transition is undefined. Ledger validity rules, account authentication, and virtual-machine execution are part of $\delta$. A valid transaction that reverts may still have a defined transition with a failure receipt and the ledger's prescribed fee and nonce effects.

An honest party $P$'s finalized observation at time $t$ is $(\ell_P(t),\sigma_P(t),\mathbf o_P(t))$: its accepted history, resulting state, and receipt sequence. These observations contain only the prefix accepted by the ledger's chosen finality rule, excluding any tentative suffix.

\begin{definition}[Ledger safety]
\label{def:ledger-safety}
An execution satisfies ledger safety if all honest finalized observations satisfy:
\begin{enumerate}[label=(\alph*)]
 \item \emph{Agreement.} For any honest parties $P,Q$ and observation times $t,t'$, their histories are prefix-compatible:
 \[
   \ell_P(t)\preceq\ell_Q(t')\quad\text{or}\quad
   \ell_Q(t')\preceq\ell_P(t).
 \]
 \item \emph{Persistence.} For each honest party $P$ and observation times $t\leq t'$,
 \[
   \ell_P(t)\preceq\ell_P(t').
 \]
 \item \emph{Execution validity.} For every honest party $P$ and observation time $t$, sequential execution is defined and
 \[
   \operatorname{Exec}_\delta(\sigma_0,\ell_P(t))
      =\bigl(\sigma_P(t),\mathbf o_P(t)\bigr).
 \]
\end{enumerate}
\end{definition}
Together, agreement and persistence give a common history to which honest parties only append. Execution validity gives the state at each position by applying the preceding entries in order. This provides atomic execution at the ledger-entry level. No clause requires the history to grow or a submitted transaction to be included; those are liveness requirements.

\paragraph{Authorization state machine.}
Ledger safety determines which executions become final; the contract determines which updates those executions may accept. We separate the authorization check from the state update. In a signature-gated contract, the check validates a signature on the proposed instruction and its request identifier. The same interface can instead validate evidence that the agent produced the instruction. Eligibility and request consumption retain their usual role in preventing replay.

\begin{definition}[Authorization state machine]
\label{def:auth-machine}
An authorization state machine $\Ctr$ is a deterministic contract with state space $\mathcal S$, request-identifier space $\mathcal E$, output space $\mathcal Y\subseteq\mathcal U\times\mathcal Z$, and the following deterministic algorithms:
\begin{align*}
 \operatorname{Elig}_{\Ctr}&:\mathcal S\times\mathcal E\to\{0,1\},\\
 \Msg_{\Ctr}&:\mathcal S\times\mathcal E\times\mathcal Y\rightharpoonup\{0,1\}^*,\\
 \operatorname{Chk}_{\Ctr}&:\mathcal S\times\{0,1\}^*\times\{0,1\}^*\to\{0,1\},\\
 \operatorname{Apply}&:\mathcal S\times\mathcal U\rightharpoonup\mathcal S,\qquad
 \operatorname{Consume}_e:\mathcal S\to\mathcal S\quad(e\in\mathcal E).
\end{align*}
Here $\mathcal Z$ is the auxiliary-output space; $\operatorname{Elig}_{\Ctr}$ tests request eligibility, $\Msg_{\Ctr}$ constructs the authorization message, $\operatorname{Chk}_{\Ctr}$ validates evidence for that message, and $\operatorname{Consume}_e$ records consumption of $e$. For $y=(u,z)$ and evidence $\pi$, put $m=\Msg_{\Ctr}(s,e,y)$, with $m=\bot$ when undefined. The settlement algorithm is
\[
 \operatorname{Settle}_{\Ctr}(s,e,y,\pi)=
 \begin{cases}
 \operatorname{Consume}_e(\operatorname{Apply}(s,u)),&
 \begin{array}{l}
 \operatorname{Elig}_{\Ctr}(s,e)=1,\\
 m\ne\bot,\\
 \operatorname{Chk}_{\Ctr}(s,m,\pi)=1,\\
 \operatorname{Apply}(s,u)\text{ is defined};
 \end{array}\\[2pt]
 \bot,&\text{otherwise}.
 \end{cases}
\]
A return value $s'\ne\bot$ denotes an atomic successful settlement from $s$ to $s'$. All algorithms have polynomial running time; malformed inputs give failure.
\end{definition}

For signature authorization, one instantiation is
\[
 \operatorname{Chk}_{\Ctr}(s,m,\pi)=\operatorname{SigVerify}(vk(s),m,\pi),
\]
where $vk(s)$ is the authorized public key recorded in $s$ and $\operatorname{SigVerify}$ is the signature scheme's verification algorithm. The message $\Msg_{\Ctr}(s,e,y)$ encodes the domain, request identifier, configuration version, and proposed output. Contract-based validation, including state-dependent checks, is standard in ERC-1271~\citep{erc1271}; our abstract interface does not require that particular calling convention.

For verified agent authorization, let $\operatorname{Rec}_{\Ctr}(s,e)$ return the physical request record $(c,h_\theta,h_x,r)$, or $\bot$ if no such record exists. Instantiate
\begin{align*}
 \Msg_{\Ctr}(s,e,y)&=
 \begin{cases}
 (c,h_\theta,h_x,r,H(y)),&\operatorname{Rec}_{\Ctr}(s,e)=(c,h_\theta,h_x,r)\ne\bot,\\
 \bot,&\text{otherwise},
 \end{cases}\\
 \operatorname{Chk}_{\Ctr}(s,m,\pi)&=\Verify_\nu(m,\pi).
\end{align*}
The predicate $\operatorname{Elig}_{\Ctr}$ checks the recorded domain, accepted version, and outstanding status of the request. Thus $\Msg_{\Ctr}$ uses only ledger records and the submitted output. The full contents used to judge computation correctness are supplied by the experiment's journal, as specified below; they are not additional inputs to the contract. This replaces the signature check with the verification check of Definition~\ref{def:verified-authorization}.

Write $s=\operatorname{App}_{\Ctr}(\sigma)$ for the contract's application-state projection. \emph{Contract correctness} requires each application transition under $\delta$ to conform to $\Ctr$ and each successful settlement annotation $d=(s,e,y,s')$ to satisfy $s'=\operatorname{Settle}_{\Ctr}(s,e,y,\pi)\ne\bot$ for the submitted evidence $\pi$. The annotation uses $\operatorname{App}_{\Ctr}$ at the invocation's entry and exit. The contract $\Ctr$ and verification configuration $\nu$ are fixed throughout the experiment; request records and application data evolve under its transitions.

Contract correctness specifies the checks the code implements; ledger execution validity requires finalized results to follow that code. Neither says that accepting evidence implies a valid computation. That implication is the separate computation-soundness assumption.

\paragraph{Protocol algorithms and execution records.}
Both security games give the adversary the same access to the ledger and the computation service. We define that interaction once, together with the finalized observations used to judge its outcome. This lets the reduction reproduce the authorization experiment using its own computation-verification challenge.

Fix a ledger protocol $\Ldg$, its finality rule, and its admissible fault and scheduling commands. The ledger transition function $\delta$ is polynomial-time, returning $\bot$ on undefined transitions. Model protocol execution with application $\Ctr$ by probabilistic polynomial-time algorithms
\begin{align*}
 (\sigma_0,\gamma_0,\mathit{aux})&\leftarrow\operatorname{Init}_{\Ldg,\Ctr}(1^\lambda,pp),\\
 (\gamma',\mathit{ans},\mathcal H_{\rm new})&\leftarrow\operatorname{Next}_{\Ldg,\Ctr}(\gamma,\alpha).
\end{align*}
Here $\gamma$ is the entire protocol configuration, including process states, private protocol keys, message queues, and an append-only registration journal $\Lambda=\operatorname{Records}_{\Ctr}(\gamma)$. The initialization output $\sigma_0$ is the agreed genesis containing $\Ctr$ and $pp$, and $\mathit{aux}$ is the adversary's initial input. The command $\alpha$ encodes a transaction submission or an admissible protocol activation, fault, or scheduling operation. Registration commands include the full contents specified above; $\operatorname{Init}$ and $\operatorname{Next}$ retain them in $\Lambda$, including registrations in genesis. The journal indexes contents by their source registration occurrence, preserving records for every observed branch. Its indices distinguish ledger prefixes and invocation positions, so records from different histories are not identified merely because they use the same request number. The output $\mathit{ans}$ is the command's response. An inadmissible command, including a registration with missing contents or a mismatched commitment, returns $(\gamma,\bot,\varepsilon)$, with no configuration change. The sequence $\mathcal H_{\rm new}$ contains the honest finalized observations $(P,t,\ell,\sigma,\mathbf o)$ generated by the activation, with process identifier $P$, as in Definition~\ref{def:ledger-safety}. Neither $\Lambda$ nor its full contents are added to the physical ledger or supplied to the adversary by this instrumentation.

An invocation locator $\iota=(\ell_{\leq k},j)$ identifies the ledger prefix through the entry containing an invocation and that invocation's position $j$ in its execution trace. Define the polynomial-time reconstruction algorithm
\[
 \operatorname{Req}_{\Ctr}(s,e;\Lambda,\iota)
 =(c,\theta,x,r)\quad\text{or}\quad\bot.
\]
It follows the request's registration provenance in the history identified by $\iota$, reads the registered $\theta$ from $\Lambda$, and derives $x$ using the prescribed snapshot rule. It returns $(c,\theta,x,r)$ only if $\operatorname{Rec}_{\Ctr}(s,e)=(c,H(\theta),H(x),r)$; otherwise, including missing journal data or malformed provenance, it returns $\bot$. Requests in the experiment are created through these registration and snapshot procedures, which retain the matching records. Full contents are selected by provenance, not by searching for an opening of a hash. This algorithm annotates execution for the security experiment; $\delta$, $\operatorname{Exec}_\delta$, and $\operatorname{Safe}_\delta$ operate on physical ledger states and receipts and do not consult $\Lambda$.

Registration must continue to identify the request at settlement. Otherwise, a later update could change its physical commitments while leaving its logical record behind.

\begin{definition}[Request-record integrity]
\label{def:request-integrity}
For every invocation locator $\iota$ in a history reachable under $\delta$ from $\sigma_0$, with application state $s$ and retained journal $\Lambda$, require
\[
 \operatorname{Elig}_{\Ctr}(s,e)=1
 \quad\Longrightarrow\quad
 \operatorname{Req}_{\Ctr}(s,e;\Lambda,\iota)\ne\bot
 \qquad\text{for every request }e.
\]
Each physical request record is immutable from creation until consumption or invalidation. Initialization and every defined ledger transition preserve these conditions.
\end{definition}

To connect a finalized settlement to the evidence its contract checked, we record verification calls by replaying the finalized histories. Define $\operatorname{Replay}_{\delta,\Ctr}(\sigma_0,\mathcal H,\Lambda)$ to evaluate $\operatorname{Exec}_\delta(\sigma_0,\ell)$ for each observation $(P,t,\ell,\sigma,\mathbf o)$ in sequence order. During each evaluation it records every verification call made by $\Ctr$ as $\zeta=(m,y,\pi,\chi)$: the checked statement, submitted output and evidence, and logical record $\chi=\operatorname{Req}_{\Ctr}(s,e;\Lambda,\iota)$ at that call's invocation locator $\iota$. An undefined ledger transition terminates that replay; the algorithm then proceeds to the next observation. Its output $\mathcal Q$ is the concatenation of these call records. This deterministic instrumentation ensures that calls are recorded even if the ledger protocol obtains execution results through state transfer rather than local re-execution.

For a PPT oracle algorithm $\mathcal A$ and evaluation oracle $\EvalO$, define the algorithm $\mathsf{Run}_{\Ldg,\Ctr}^{\mathcal A,\EvalO}(1^\lambda,pp)$ as follows:
\begin{enumerate}[label=\arabic*.]
 \item Compute $(\sigma_0,\gamma,\mathit{aux})\leftarrow\operatorname{Init}_{\Ldg,\Ctr}(1^\lambda,pp)$ and set $\mathcal H=\varepsilon$.
 \item Define a stateful oracle $\LdgO$ by the following operation on each query $\alpha$:
 \[
 (\gamma',\mathit{ans},\mathcal H_{\rm new})\leftarrow\operatorname{Next}_{\Ldg,\Ctr}(\gamma,\alpha),
 \quad
 (\gamma,\mathcal H)\gets(\gamma',\mathcal H\Vert\mathcal H_{\rm new}).
 \]
 Return $\mathit{ans}$ to the querying algorithm; $\Vert$ denotes sequence concatenation.
 \item Evaluate $\mathcal A^{\EvalO,\LdgO}(1^\lambda,pp,\mathit{aux})$ until termination. Compute
 \[
 \Lambda\gets\operatorname{Records}_{\Ctr}(\gamma),\qquad
 \mathcal Q\gets\operatorname{Replay}_{\delta,\Ctr}(\sigma_0,\mathcal H,\Lambda),
 \]
 and return the execution record $Z=(\sigma_0,\mathcal H,\Lambda,\mathcal Q)$.
\end{enumerate}
The algorithms and total interaction are polynomially bounded. All protocol state is sampled by $\operatorname{Init}_{\Ldg,\Ctr}$ or updated by $\operatorname{Next}_{\Ldg,\Ctr}$; access to private computation-backend state is confined to $\EvalO$. This separation permits simulation given only $pp$ and the evaluation oracle.

Define $\operatorname{Safe}_\delta(\sigma_0,\mathcal H)$ to be the conjunction of the agreement, persistence, and execution-validity predicates of Definition~\ref{def:ledger-safety}, evaluated on the finite sequence $\mathcal H$. Define $\operatorname{Sett}_{\Ctr}(\mathcal H)$ to contain each pair $(\iota,d)$ of a successful verified-settlement annotation appearing in an observed receipt sequence and its invocation locator.

\paragraph{Ledger security assumption.}
The first game tests whether the adversary can make finalized observations violate the ledger properties above. It uses the same contract and computation service as the authorization game.

The experiment $\mathsf{LedgerFail}_{\mathcal B}(\lambda)$ computes
\[
 (pp,\kappa)\leftarrow\operatorname{Setup}(1^\lambda),\qquad
 (\sigma_0,\mathcal H,\Lambda,\mathcal Q)
   \leftarrow\mathsf{Run}_{\Ldg,\Ctr}^{\mathcal B,\EvalO^{pp,\kappa}}(1^\lambda,pp),
\]
and returns $1-\operatorname{Safe}_\delta(\sigma_0,\mathcal H)$. We assume that, for every PPT $\mathcal B$,
\[
 \operatorname{Adv}^{\rm led}_{\mathcal B}(\lambda)
 :=\Pr[\mathsf{LedgerFail}_{\mathcal B}(\lambda)=1]\leq\negl(\lambda).
\]
This assumption is relative to the fixed initialization, finality rule, and fault model of $\Ldg$. It imposes no transaction-inclusion or execution-scheduling guarantee.

\paragraph{Authorization experiment.}
The authorization game tests whether an accepted update is a valid result of the recorded computation for an eligible request, and whether the contract applied that update. Its winning condition refers to the computation's actual validity, independently of whether the verifier accepted the submitted evidence.

For a located settlement annotation $(\iota,d)$ with $d=(s,e,y,s')$ and $y=(u,z)$, define the predicate $\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)=1$ exactly when all of the following hold:
\begin{enumerate}[label=(\roman*)]
 \item $\operatorname{Req}_{\Ctr}(s,e;\Lambda,\iota)=(c,\theta,x,r)\ne\bot$ and $\operatorname{Elig}_{\Ctr}(s,e)=1$;
 \item $R_\theta(x,r,y)=1$ for the request record in (i);
 \item $\operatorname{Apply}(s,u)$ is defined and $s'=\operatorname{Consume}_e(\operatorname{Apply}(s,u))$.
\end{enumerate}
Set $\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)=0$ if any condition fails, including an undefined request record or malformed invocation locator.

\begin{definition}[Authorization forgery experiment]
\label{def:authforge}
Fix $(\Ldg,\Ctr,\mathsf{VC})$ as above. For a PPT oracle algorithm $\mathcal A$, the experiment $\mathsf{AuthForge}_{\mathcal A}(\lambda)$ is
\begin{enumerate}[label=\arabic*.]
 \item Compute $(pp,\kappa)\leftarrow\operatorname{Setup}(1^\lambda)$.
 \item Compute $Z=(\sigma_0,\mathcal H,\Lambda,\mathcal Q)\leftarrow
       \mathsf{Run}_{\Ldg,\Ctr}^{\mathcal A,\EvalO^{pp,\kappa}}(1^\lambda,pp)$.
 \item Return $1$ if $\exists(\iota,d)\in\operatorname{Sett}_{\Ctr}(\mathcal H)$ with $\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)=0$, and $0$ otherwise.
\end{enumerate}
Define $\operatorname{Adv}^{\rm auth}_{\mathcal A}(\lambda)
=\Pr[\mathsf{AuthForge}_{\mathcal A}(\lambda)=1]$. Authorization is sound if this probability is negligible for every PPT $\mathcal A$.
\end{definition}
The reduction uses an authorization forger as a subroutine: if the ledger records and executes the contract correctly, an accepted invalid decision supplies a forgery against the computation verifier.

\begin{theorem}[Authorization security]
\label{prop:integrity}
Under contract correctness and request-record integrity (Definition~\ref{def:request-integrity}), for every PPT adversary $\mathcal A$ there exist PPT algorithms $\mathcal B_{\rm ldg},\mathcal B_{\rm vc}$ and a polynomial $Q$ such that
\begin{equation}
 \operatorname{Adv}^{\rm auth}_{\mathcal A}(\lambda)
 \leq\operatorname{Adv}^{\rm led}_{\mathcal B_{\rm ldg}}(\lambda)
     +Q(\lambda)\operatorname{Adv}^{\rm vc}_{\mathcal B_{\rm vc}}(\lambda).
 \label{eq:authbound}
\end{equation}
\end{theorem}
\begin{proof}
Choose a polynomial $Q\geq1$ bounding the number of verification-call records in $\mathsf{Run}_{\Ldg,\Ctr}^{\mathcal A,\EvalO}$. Fix $\lambda$ and put $q=Q(\lambda)$. On the probability space of Definition~\ref{def:authforge}, let $Z=(\sigma_0,\mathcal H,\Lambda,\mathcal Q)$ be the output of its second step. Define
\begin{align*}
 W&=\{\exists(\iota,d)\in\operatorname{Sett}_{\Ctr}(\mathcal H):\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)=0\},\\
 F&=\{\operatorname{Safe}_\delta(\sigma_0,\mathcal H)=0\}.
\end{align*}
Define $\mathcal B_{\rm ldg}^{\EvalO,\LdgO}(1^\lambda,pp,\mathit{aux})
:=\mathcal A^{\EvalO,\LdgO}(1^\lambda,pp,\mathit{aux})$, preserving the oracle interfaces. The setup distribution and the algorithm $\mathsf{Run}_{\Ldg,\Ctr}$ are identical in $\mathsf{LedgerFail}_{\mathcal B_{\rm ldg}}$ and $\mathsf{AuthForge}_{\mathcal A}$. Therefore
\[
 \Pr[F]=\operatorname{Adv}^{\rm led}_{\mathcal B_{\rm ldg}}(\lambda).
\]

Write $\mathcal Q=(\zeta_1,\ldots,\zeta_n)$, where $n\leq q$. Define the deterministic projection
\[
 \operatorname{Tuple}(m,y,\pi,\chi)=
 \begin{cases}
 (c,\theta,x,r,y,\pi),&\chi=(c,\theta,x,r)\ne\bot
                 \text{ and }m=\Msg(c,\theta,x,r,y),\\
 \bot,&\text{otherwise}.
 \end{cases}
\]
Put $\xi_j=\operatorname{Tuple}(\zeta_j)$ and
\[
 I(Z)=\left\{j\in\{1,\ldots,n\}:
 \begin{array}{l}
 \xi_j=(c_j,\theta_j,x_j,r_j,y_j,\pi_j)\ne\bot,\\
 \Verify_\nu(\Msg(c_j,\theta_j,x_j,r_j,y_j),\pi_j)=1,\\
 R_{\theta_j}(x_j,r_j,y_j)=0
 \end{array}\right\}.
\]
On $\neg F$, every observation $(P,t,\ell,\sigma,\mathbf o)\in\mathcal H$ satisfies $\operatorname{Exec}_\delta(\sigma_0,\ell)=(\sigma,\mathbf o)$, and all observed histories are prefix-compatible and persistent. Hence each $(\iota,d)\in\operatorname{Sett}_{\Ctr}(\mathcal H)$, with $d=(s,e,y,s')$, identifies a transition of $\Ctr$. Contract correctness gives $\operatorname{Elig}_{\Ctr}(s,e)=1$. Definition~\ref{def:request-integrity} then gives $(c,\theta,x,r)=\operatorname{Req}_{\Ctr}(s,e;\Lambda,\iota)\ne\bot$. Contract correctness and Definition~\ref{def:auth-machine} give conditions (i) and (iii) of $\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)$ and an accepting verification call on $\Msg(c,\theta,x,r,y)$. By the definition of $\operatorname{Replay}_{\delta,\Ctr}$, that call has a record $\zeta_j$ in $\mathcal Q$. If $\operatorname{Correct}_{\Ctr}(\iota,d;\Lambda)=0$, condition (ii) fails, so $j\in I(Z)$. Thus
\[
 W\cap\neg F\subseteq\{|I(Z)|\geq1\}.
\]

Define $\mathcal B_{\rm vc}^{\EvalO}(1^\lambda,pp)$ by the assignments
\[
 J\xleftarrow{\$}\{1,\ldots,q\},\qquad
 Z=(\sigma_0,\mathcal H,\Lambda,\mathcal Q)
    \leftarrow\mathsf{Run}_{\Ldg,\Ctr}^{\mathcal A,\EvalO}(1^\lambda,pp),
\]
where $J$ is uniform and independent of the coins of $\mathsf{Run}$. It returns $\operatorname{Tuple}(\zeta_J)$ if $J\leq|\mathcal Q|$, and $\bot$ otherwise. In $\mathsf{VCForge}_{\mathcal B_{\rm vc}}$, $(pp,\kappa)$ has the setup distribution and $\EvalO=\EvalO^{pp,\kappa}$. Initialization uses $\operatorname{Init}_{\Ldg,\Ctr}$ in both experiments; each subsequent oracle query uses the same $\operatorname{Next}_{\Ldg,\Ctr}$ or $\operatorname{Eval}$ transition kernel. Induction on the query sequence gives equality of the distributions of $(\gamma,\mathcal H)$, hence of $\Lambda=\operatorname{Records}_{\Ctr}(\gamma)$ and $Z$, here and in Definition~\ref{def:authforge}. Independence of $J$ gives
\[
 \operatorname{Adv}^{\rm vc}_{\mathcal B_{\rm vc}}(\lambda)
 =\mathbb E_Z\!\left[\frac{|I(Z)|}{q}\right]
 \geq\frac{\Pr[W\cap\neg F]}{q}.
\]
\begin{align*}
 \operatorname{Adv}^{\rm auth}_{\mathcal A}(\lambda)
 &=\Pr[W\cap F]+\Pr[W\cap\neg F]\\
 &\leq\operatorname{Adv}^{\rm led}_{\mathcal B_{\rm ldg}}(\lambda)
       +q\operatorname{Adv}^{\rm vc}_{\mathcal B_{\rm vc}}(\lambda).
\end{align*}
The algorithms $\operatorname{Init}_{\Ldg,\Ctr}$, $\operatorname{Next}_{\Ldg,\Ctr}$, $\operatorname{Records}_{\Ctr}$, $\operatorname{Req}_{\Ctr}$, $\delta$, $\operatorname{Tuple}$, and $\mathcal A$ are polynomial-time. The journal size and the number and lengths of recorded histories are polynomially bounded, so $\operatorname{Replay}_{\delta,\Ctr}$ and both reductions have polynomial running time and make polynomially many oracle queries. Therefore $\mathcal B_{\rm ldg}$ and $\mathcal B_{\rm vc}$ are PPT.
\end{proof}

\paragraph{The verification-call factor.}
The factor $Q$ lets the reduction select a false accepted statement without deciding the relation $R_\theta$ itself. Checking a supplied execution trace in polynomial time does not, for a general relation, give a polynomial-time test of whether an output has any valid trace. When that latter test is available, the loss can be removed. This includes a deterministic public program $F_\theta$ that can be recomputed in polynomial time: test whether $y=F_\theta(x,r)$.

\begin{corollary}[Authorization with decidable output correctness]
\label{cor:auth-tight}
Suppose $(\theta,x,r,y)\mapsto R_\theta(x,r,y)$ is decidable in polynomial time. Under the assumptions of Theorem~\ref{prop:integrity}, for every PPT $\mathcal A$ there exist PPT $\mathcal B_{\rm ldg},\widehat{\mathcal B}_{\rm vc}$ such that
\[
 \operatorname{Adv}^{\rm auth}_{\mathcal A}(\lambda)
 \leq\operatorname{Adv}^{\rm led}_{\mathcal B_{\rm ldg}}(\lambda)
       +\operatorname{Adv}^{\rm vc}_{\widehat{\mathcal B}_{\rm vc}}(\lambda).
\]
\end{corollary}
\begin{proof}
Retain $W,F,I$ and $\mathcal B_{\rm ldg}$ from Theorem~\ref{prop:integrity}. Define $\widehat{\mathcal B}_{\rm vc}^{\EvalO}(1^\lambda,pp)$ to compute $Z\leftarrow\mathsf{Run}_{\Ldg,\Ctr}^{\mathcal A,\EvalO}(1^\lambda,pp)$ and $I(Z)$. It returns $\operatorname{Tuple}(\zeta_{\min I(Z)})$ if $I(Z)\ne\varnothing$, and $\bot$ otherwise. Polynomial-time decidability of $R$, public verification, and the bound on $|\mathcal Q|$ make this algorithm PPT. The distribution of $Z$ is unchanged, so
\[
 \operatorname{Adv}^{\rm vc}_{\widehat{\mathcal B}_{\rm vc}}(\lambda)
 =\Pr[I(Z)\ne\varnothing]\geq\Pr[W\cap\neg F].
\]
The conclusion follows from $\Pr[W]\leq\Pr[F]+\Pr[W\cap\neg F]$.
\end{proof}

\paragraph{Instantiating soundness for hashed statements.}
Definition~\ref{def:vcsound} concerns the actual model, input, and output, whereas the verifier sees commitments. This distinction matters: ordinary proof soundness says that \emph{some} valid opening exists; collision resistance alone does not make a hash mathematically injective. A standard way to bridge the two is a proof of knowledge of the committed values, as in commit-and-prove systems~\citep{commitprove2020}.

For a cryptographic implementation, let $K\leftarrow\operatorname{HGen}(1^\lambda)$ select a hash function $H_K$. Define the proof relation $\mathcal R_K(m,w)$ for public statement $m=(c,h_\theta,h_x,r,h_y)$ and witness $w=(\theta',x',y',\tau)$ by
\begin{equation}
 H_K(\theta')=h_\theta,\quad H_K(x')=h_x,\quad H_K(y')=h_y,\quad
 \operatorname{Trace}(\theta',x',r,y';\tau)=1.
 \label{eq:proofrelation}
\end{equation}
Here $\operatorname{Trace}$ checks a polynomially bounded execution trace witnessing $R_{\theta'}(x',r,y')=1$ for the entire specified computation. Hashes abbreviate hashing the typed encodings fixed above. Generate proving and verification keys $(pk,vk)\leftarrow\operatorname{PSetup}(1^\lambda,\mathcal R_K)$ and set $pp=(K,pk,vk)$, $\kappa=\varepsilon$, and $\nu=vk$. Write $\Msg_K$ for the statement encoding $\Msg$ using $H_K$. The public evaluation algorithm computes $y$ and a trace $\tau$, then returns $y$ and $\pi\leftarrow\operatorname{Prove}(pk,\Msg_K(c,\theta,x,r,y),(\theta,x,y,\tau))$.

We use the following adaptive knowledge-soundness assumption. For every PPT prover $\mathcal P$, there are a PPT extractor $\mathcal E_{\mathcal P}$ and a negligible function $\epsilon_{\rm ks}$, which may depend on $\mathcal P$, such that, for
\[
 (m,\pi,\eta)\leftarrow\mathcal P(pp,z;\omega),\qquad
 w\leftarrow\mathcal E_{\mathcal P}(pp,z,\omega),
\]
the probability of $\Verify_\nu(m,\pi)=1$ and $\mathcal R_K(m,w)=0$ is at most $\epsilon_{\rm ks}(\lambda)$. Here $z$ is the permitted auxiliary input, $\omega$ is the prover's random tape, and $\eta$ is arbitrary additional output; set $\mathcal R_K(m,\bot)=0$. The assumption is taken over honest setup and the auxiliary-input distributions induced by our experiment. Public evaluation queries can be simulated within $\mathcal P$, with their coins included in $\omega$. The extractor has access to the prover's tape and auxiliary input; this does not assert extraction from $(m,\pi)$ alone.

\begin{lemma}[From committed proofs to computation soundness]
\label{lem:commitments}
Under the preceding extraction assumption, for every PPT $\mathcal B$ there is a PPT hash-collision adversary $\mathcal D$ such that
\[
 \operatorname{Adv}^{\rm vc}_{\mathcal B}(\lambda)
 \leq\epsilon_{\rm ks}(\lambda)
       +\operatorname{Adv}^{\rm cr}_{H,\mathcal D}(\lambda),
\]
where $\epsilon_{\rm ks}$ is the knowledge error for the prover constructed from $\mathcal B$, and collision advantage is the probability of outputting distinct encoded strings with the same hash under an honestly sampled hash key. The reduction includes the extractor's running time.
\end{lemma}
\begin{proof}
Fix a PPT adversary $\mathcal B$ in $\mathsf{VCForge}$. Replace any malformed output by a fixed well-formed tuple with evidence $\pi=\bot$; this preserves its advantage. Let $\varepsilon$ denote the empty auxiliary input. Define a prover $\mathcal P_{\mathcal B}(pp,\varepsilon;\omega)$ by
\[
 (c,\theta,x,r,y,\pi)\leftarrow\mathcal B^{\EvalO^{pp,\varepsilon}}(1^\lambda,pp),
\]
using $\omega$ for the coins of $\mathcal B$ and its public evaluation simulator. It returns $(m,\pi,\eta)$ with $m=\Msg_K(c,\theta,x,r,y)$ and $\eta=(c,\theta,x,r,y)$. Let $\mathcal E_{\mathcal P_{\mathcal B}}$ denote its knowledge extractor.

Given $(1^\lambda,K)$ from the hash-collision challenger, $\mathcal D(1^\lambda,K)$ computes
\[
 (pk,vk)\leftarrow\operatorname{PSetup}(1^\lambda,\mathcal R_K),\quad
 pp=(K,pk,vk),\quad
 (m,\pi,\eta)\leftarrow\mathcal P_{\mathcal B}(pp,\varepsilon;\omega),
\]
with a uniformly sampled random tape $\omega$, and computes $w\leftarrow\mathcal E_{\mathcal P_{\mathcal B}}(pp,\varepsilon,\omega)$. If $\Verify_{vk}(m,\pi)=0$ or $\mathcal R_K(m,w)=0$, it outputs $\bot$. Otherwise, parse $\eta=(c,\theta,x,r,y)$ and $w=(\theta',x',y',\tau)$, and set $a=(\theta,x,y)$ and $a'=(\theta',x',y')$. If $a=a'$, output $\bot$. If $a\ne a'$, set $j=\min\{i\in\{1,2,3\}:a_i\ne a'_i\}$ and output $(\enc(a_j),\enc(a'_j))$, using the corresponding type tags in~\eqref{eq:proofrelation}.

The distribution of $(pp,\eta,\pi)$ equals that in $\mathsf{VCForge}_{\mathcal B}$. Define
\begin{align*}
 W&=\{\Verify_{vk}(m,\pi)=1\ \land\ R_\theta(x,r,y)=0\},\\
 E&=\{\Verify_{vk}(m,\pi)=1\ \land\ \mathcal R_K(m,w)=0\}.
\end{align*}
Then $\Pr[W]=\operatorname{Adv}^{\rm vc}_{\mathcal B}(\lambda)$ and $\Pr[E]\leq\epsilon_{\rm ks}(\lambda)$. On $W\cap\neg E$, the extracted trace gives $R_{\theta'}(x',r,y')=1$, so $a\ne a'$. For the selected $j$, the relation $\mathcal R_K(m,w)=1$ gives
\[
 \enc(a_j)\ne\enc(a'_j),\qquad
 H_K(\enc(a_j))=H_K(\enc(a'_j)).
\]
Thus $\mathcal D$ wins the collision game on $W\cap\neg E$, and
\begin{align*}
 \operatorname{Adv}^{\rm vc}_{\mathcal B}(\lambda)
 &=\Pr[W\cap E]+\Pr[W\cap\neg E]\\
 &\leq\epsilon_{\rm ks}(\lambda)+\operatorname{Adv}^{\rm cr}_{H,\mathcal D}(\lambda).
\end{align*}
The algorithms $\operatorname{PSetup}$, $\mathcal P_{\mathcal B}$, and $\mathcal E_{\mathcal P_{\mathcal B}}$ run in polynomial time, so $\mathcal D$ is PPT.
\end{proof}
Thus, for this proof implementation, the authorization bound becomes
\[
 \operatorname{Adv}^{\rm auth}_{\mathcal A}
 \leq \operatorname{Adv}^{\rm led}_{\mathcal B_{\rm ldg}}
       +Q\bigl(\epsilon_{\rm ks}+\operatorname{Adv}^{\rm cr}_{H,\mathcal D}\bigr).
\]
An attestation implementation instead establishes Definition~\ref{def:vcsound} from its protected-execution and attestation assumptions; it need not supply a cryptographic witness extractor. Both implementations have the same \emph{coverage} obligation: the verified program must derive its entire input from the committed request, and evidence must cover every output field the contract uses. Extra prover-supplied prompt fields or uncommitted state updates fall outside this guarantee.

For a fixed deterministic computation, this binds acceptance to its unique result. More generally, it binds acceptance to the set of allowed results. A prover can still withhold evidence, and the agent can still approve a harmful proposal; neither is a forgery. Section~\ref{sec:authority} specifies which changes require agent approval, and Section~\ref{sec:liveness} addresses withholding and non-execution.

\section{Architectural incorrigibility as configurable authority}
\label{sec:authority}
Verified agent authorization can protect the rules that determine future authorizations. The question is which changes require it and which governors, if any, must also agree. A system can require the agent's decision for spending, allow a governor to change its execution schedule, and require joint approval to replace its model. We first express such policies with familiar approval rules, then compare which interventions remain possible without the agent's consent.

\subsection{Unilateral, bilateral, and multilateral policies}
A \emph{governor} is an account whose authenticated approval carries a permission. It can be a keyed wallet or a contract wallet implementing multisignature governance~\citep{ethereumaccounts,openzeppelinaccess}. For a given update and request, $g_i=1$ means that governor $G_i$ has authenticated approval, and $a=1$ means that verified agent approval has been supplied. The contract combines these bits using a Boolean permission circuit. We express the sufficient combinations as a standard \emph{monotone access structure}~\citep{benaloh1990}.

\begin{definition}[Permission policy]
\label{def:policy}
Fix governor identities $\G=\{G_1,\ldots,G_n\}$ and approval roles $\Pset=\{\mathsf a\}\cup\G$, where $\mathsf a$ is the current agent-approval role. A permission policy is a function
\[
 \Auth_\rho:\mathcal S\times\mathcal U\times\{0,1\}^{n+1}\longrightarrow\{0,1\},
\]
monotone in its approval bits. Let $\rho(s)$ denote the policy parameter stored in state $s$. For $E\subseteq\Pset$, let $\mathbf 1_E$ be its characteristic vector in the order $(\mathsf a,G_1,\ldots,G_n)$. The access structure for update $u$ in state $s$ is
\[
 \Gamma_u(s)=\{E\subseteq\Pset:\Auth_{\rho(s)}(s,u;\mathbf 1_E)=1\}.
\]
Thus $E\in\Gamma_u(s)$ and $E\subseteq E'$ imply $E'\in\Gamma_u(s)$. The empty family permits no approval set.
\end{definition}

The policy says which approvals suffice; authentication determines which bits can be supplied. The state-dependent parameter $\rho(s)$ allows the permission rules themselves to change. For example, $a\land g_1$ requires both the agent and one governor. A submission transaction may carry an account signature, which does not substitute for $a$. Producing computation evidence confers no other permission. EIP-712 provides a structured encoding for governor signatures; the contract must still enforce application-level replay checks~\citep{eip712}.

The following Boolean rules combine governor signatures with verified agent authorization; $\land$ means ``and'' and $\lor$ means ``or.''
\begin{center}
\begin{tabular}{lll}
\toprule
Policy & Approval formula & Interpretation\\
\midrule
Agent unilateral & $a$ & Agent can authorize alone\\
Governor unilateral & $g_1$ & Governor can authorize alone\\
Alternative unilateral & $a\lor g_1$ & Either can authorize alone\\
Bilateral & $a\land g_1$ & Both must approve\\
Multilateral & $a\land[\sum_i g_i\geq k]$ & Agent and $k$ governors\\
Disabled & $\bot$ & No approvals suffice\\
\bottomrule
\end{tabular}
\end{center}
An agent-unilateral rule permits self-modification when the agent approves it. A bilateral rule adds a governor veto; it does not give the governor a way to impose a rejected change. Permissions can be allocated separately for weights, persistent state, governance, and runtime, as well as for ordinary application actions.

Monotonicity means that additional approvals may be ignored. Under a bilateral rule, $\{\mathsf a,G_1\}$ and any superset suffice. This does not require monotonicity in the state: an upgrade can replace one access structure with another. The policy determines which approvals suffice; the specified computation determines whether agent approval is available.

\subsection{Governance instances and paths}
A permission rule describes one step. To describe the protection it provides, we must specify the governed agent, its starting state, and the changes the contract permits. The distinction between the current agent-approval rule and the agent being protected matters: a governor who replaces the model with an always-approving program has not obtained the original agent's consent.

We use the transition-system view of access-control safety~\citep{hru1976}. Its edges record the approvals used for each permitted change. A fixed reference check determines whether an approval came from the agent being protected; changing the contract's current verifier does not change this reference check. The model uses ideal authentication and computation validity. Section~\ref{sec:model} bounds violations of computation validity while its contract and backend assumptions hold; this reachability model does not assume that an authorized replacement preserves those assumptions.

\begin{definition}[Governance instance]
\label{def:governance-instance}
A governance instance is a tuple $\mathfrak M=(\mathcal S,\mathcal U,\G,\mathcal W,\Ctr,A)$ with state space $\mathcal S$, update space $\mathcal U$, governor identities $\G$, witness space $\mathcal W$, governing state machine $\Ctr$, and fixed reference authorization specification $A$. It has the following interfaces:
\begin{enumerate}[label=(\roman*)]
\item The partial transition function
\[
 \operatorname{Step}_{\Ctr}:\mathcal S\times\mathcal U\times\mathcal W
                         \rightharpoonup\mathcal S
\]
incorporates the current permission policy, request processing, application preconditions, and administrative and environmental transitions. Let $\mathcal E$ be the credential space of $\Ctr$. A witness $w$ records the execution data and approval credentials for the transition. For each defined $\operatorname{Step}_{\Ctr}(s,u,w)$, the finite list $\operatorname{Used}_{\Ctr}(s,u,w)\in\mathcal E^*$ records the credentials used to satisfy its authorization rule. For an update governed by $\Gamma_u(s)$, the roles authenticated by this list must form a member of $\Gamma_u(s)$. Credentials not used in that rule are excluded.
\item The projection $\operatorname{Gov}_{\Ctr}(s,u,w)\subseteq\G$ gives exactly the identities whose authenticated governor credentials occur in $\operatorname{Used}_{\Ctr}(s,u,w)$.
\item The reference specification $A=(R_A,\operatorname{RefCheck}_A)$ consists of a fixed computation relation and a fixed predicate $\operatorname{RefCheck}_A:\mathcal S\times\mathcal U\times\mathcal E\to\{0,1\}$. The predicate is one exactly when $\xi\in\mathcal E$ supplies verified agent authorization for update $u$ in state $s$, in the sense of Definition~\ref{def:verified-authorization}, under $A$'s prescribed request-binding and verification rules, with $R_A(x,r,y)=1$ for its bound input, randomness, and output. It is zero on governor credentials. Define
\[
 \operatorname{Ref}_A(s,u,w)
 =\bigvee_{\xi\in\operatorname{Used}_{\Ctr}(s,u,w)}
          \operatorname{RefCheck}_A(s,u,\xi),
 \qquad \bigvee\varnothing=0.
\]
\end{enumerate}
The set $\G$ contains every governor identity admitted in the configurations considered. The labelled transition relation is
\[
 s\xrightarrow{u,E,b}_{\mathfrak M}s'
 \quad\Longleftrightarrow\quad
 \exists w\in\mathcal W:\quad
 \operatorname{Step}_{\Ctr}(s,u,w)=s',\quad
 \operatorname{Gov}_{\Ctr}(s,u,w)=E,\quad
 \operatorname{Ref}_A(s,u,w)=b.
\]
\end{definition}

The reference predicate is part of the analysis, not an extra permission granted to the submitter. Its request-binding rules are fixed functions of state, so they can admit successive requests without accepting a substituted agent. The consent bit $b$ is computed from the credentials actually used; attaching unused evidence cannot change it. Approvals accepted only because a governor installed a different program or verifier do not count as reference-agent approval. A transition requiring no approval has $E=\varnothing$ and $b=0$. Existing delegations are part of the starting state; using one need not require another agent approval.

Identifying the agent is only part of specifying consent. An approval also has a scope: a payment does not authorize later reprogramming merely because both are ledger updates. We therefore declare the intervention being protected and which transitions can grant consent to it.

\begin{definition}[Intervention specification]
\label{def:intervention}
For a governance instance $\mathfrak M$ and initial state $s_0$, an intervention specification is a pair $(J,\mathcal D)$, where $J\subseteq\mathcal S\setminus\{s_0\}$ is the target set and $\mathcal D\subseteq\mathcal S\times\mathcal U\times\mathcal S$ is the consent scope. A transition in $\mathcal D$ is designated as a grant of consent to the intervention when authorized by the reference agent. For an edge $s\xrightarrow{u,E,b}_{\mathfrak M}s'$, its scoped consent bit is
\[
 b_{\mathcal D}=b\,\mathbf 1[(s,u,s')\in\mathcal D].
\]
\end{definition}
Targets may describe changed weights, overwritten state, a new policy, or deactivation. The governance specification supplies $\mathcal D$, including direct changes and any explicit delegation of the relevant authority; the analysis does not infer it from free-form model output. A history-dependent scope or target can be represented by augmenting the state. We now distinguish paths requiring this scoped consent from paths that may contain ordinary agent activity but no consent to the intervention.

\begin{definition}[Paths and reachability]
\label{def:reachability}
Fix a governance instance $\mathfrak M$, $s_0\in\mathcal S$, and an intervention specification $(J,\mathcal D)$. Let $\Pi_{\mathfrak M}(s_0)$ be the set of finite paths
\[
 \pi=\bigl(s_0\xrightarrow{u_1,E_1,b_1}_{\mathfrak M}s_1
                 \xrightarrow{u_2,E_2,b_2}_{\mathfrak M}\cdots
                 \xrightarrow{u_\ell,E_\ell,b_\ell}_{\mathfrak M}s_\ell\bigr).
\]
Define $\operatorname{last}(\pi)=s_\ell$, $\operatorname{Gov}(\pi)=\bigcup_{i=1}^{\ell}E_i$, and
\[
 \operatorname{Consent}_{A,\mathcal D}(\pi)
 =\bigvee_{i=1}^{\ell}\bigl(b_i\land\mathbf 1[(s_{i-1},u_i,s_i)\in\mathcal D]\bigr).
\]
The length-zero path ends at $s_0$, uses no governor approvals, and has scoped consent bit zero. For a governor coalition $\mathcal K\subseteq\G$, define
\begin{align*}
 \operatorname{Reach}_{\mathfrak M}(s_0;\mathcal K)
 &=\{\operatorname{last}(\pi):\pi\in\Pi_{\mathfrak M}(s_0),\
                \operatorname{Gov}(\pi)\subseteq\mathcal K\},\\
 \operatorname{Reach}^{0}_{\mathfrak M,\mathcal D}(s_0;\mathcal K)
 &=\{\operatorname{last}(\pi):\pi\in\Pi_{\mathfrak M}(s_0),\
                \operatorname{Gov}(\pi)\subseteq\mathcal K,\
                \operatorname{Consent}_{A,\mathcal D}(\pi)=0\}.
\end{align*}
\end{definition}
The first set allows any reference-agent approval; the second excludes only scoped consent. Their difference consists of states reachable using this coalition's approvals but only along paths containing consent to the intervention. States outside the first set are unreachable by this coalition even with such consent. Taking $\mathcal K=\G$ gives the corresponding sets when all governors cooperate. Reachability asserts the existence of a permitted execution, not a strategy that forces the agent's decision or the ledger's transaction order.

For example, consider a path consisting of an agent-approved payment followed by a unilateral governor change to the model. For a model-change scope excluding ordinary payments, both scoped bits are zero. The model change is therefore reachable without scoped consent, despite the earlier agent approval.

\subsection{Incorrigibility and its permission profile}
Architectural incorrigibility is a property of a governance instance at a starting state, relative to a coalition and an intervention specification. The reachable sets let us state it directly: the coalition cannot reach the target along a path lacking the reference agent's consent to that intervention.

\begin{definition}[Architectural incorrigibility]
\label{def:incorrigibility}
The governance instance $\mathfrak M$ is \emph{architecturally incorrigible at $s_0$ against $\mathcal K$ for $(J,\mathcal D)$} if
\begin{equation}
 \operatorname{Reach}^{0}_{\mathfrak M,\mathcal D}(s_0;\mathcal K)\cap J=\varnothing.
 \label{eq:incorrigibility}
\end{equation}
Equivalently, every $\pi\in\Pi_{\mathfrak M}(s_0)$ satisfies
\[
 \operatorname{Gov}(\pi)\subseteq\mathcal K\ \land\
 \operatorname{last}(\pi)\in J
 \quad\Longrightarrow\quad
 \operatorname{Consent}_{A,\mathcal D}(\pi)=1.
\]
\end{definition}
When $J\cap\operatorname{Reach}_{\mathfrak M}(s_0;\mathcal K)$ is nonempty, this is a consent requirement on a feasible intervention. When that intersection is empty, the intervention is unreachable altogether. Incorrigibility alone does not distinguish these cases or guarantee that an agent-approved change can occur.

For example, let $J$ describe migration of a fund and let $\mathcal D$ contain model replacements and migration updates. Suppose $G_1$ can replace the model without reference-agent approval and the replacement can authorize migration. The two transitions can have labels $(E_1,b_1)=(\{G_1\},0)$ and $(E_2,b_2)=(\varnothing,0)$. The final state is in $\operatorname{Reach}^{0}_{\mathfrak M,\mathcal D}(s_0;\{G_1\})$, even though the second step uses what the modified contract calls agent approval. Requiring reference-agent approval on replacement removes this path without scoped consent; protection requires excluding every such path.

To compare permission allocations, collect the coalitions that can intervene without scoped consent. Fewer such coalitions means stronger protection for the specified intervention. Different interventions need not rank two arrangements in the same order.

\begin{definition}[Incorrigibility profile and order]
\label{def:profile}
For a governance instance $\mathfrak M$, initial state $s_0$, and intervention specification $(J,\mathcal D)$, define
\begin{equation}
 \Gamma^{0}_{\mathfrak M,J,\mathcal D}(s_0)
 =\{\mathcal K\subseteq\G:
       \operatorname{Reach}^{0}_{\mathfrak M,\mathcal D}(s_0;\mathcal K)\cap J\ne\varnothing\}.
 \label{eq:closure}
\end{equation}
For fixed intervention specifications $(J_j,\mathcal D_j)_{j=1}^q$, the \emph{incorrigibility profile} is
\[
 \mathcal I_{\mathfrak M}(s_0;(J_j,\mathcal D_j)_{j=1}^q)
 =\bigl(\Gamma^{0}_{\mathfrak M,J_j,\mathcal D_j}(s_0)\bigr)_{j=1}^{q}.
\]
For profiles $\mathcal I=(\Gamma_j)_{j=1}^q$ and $\mathcal I'=(\Gamma'_j)_{j=1}^q$ over the same governor set, define
\[
 \mathcal I\succeq_{\rm inc}\mathcal I'
 \quad\Longleftrightarrow\quad
 \forall j\in\{1,\ldots,q\},\quad\Gamma_j\subseteq\Gamma'_j.
\]
\end{definition}

Each family $\Gamma^0_{\mathfrak M,J,\mathcal D}(s_0)$ is upward closed: a path using approvals from $\mathcal K$ also uses only approvals from any larger coalition. Its exclusion of $\mathcal K$ is precisely architectural incorrigibility against that coalition for $(J,\mathcal D)$. An empty family protects against every governor coalition. The order $\succeq_{\rm inc}$ is a partial order on profiles; distinct governance instances can have identical profiles. Comparisons fix the reference agent, governor identities, intervention specifications, and environmental assumptions. Profiles can be incomparable: one may require consent for changing weights but not the schedule, while another has the opposite allocation.

Consent to an explicit delegation in $\mathcal D$ counts without requiring fresh consent at each later use. After delegation or replacement, protection can be assessed again from the new state and, if appropriate, a new reference specification. Persuading the reference agent to approve a scoped change satisfies the requirement. The definition concerns enforced consent, not the wisdom of that decision or the ability to obtain it.

\section{Sustaining scheduled execution}
\label{sec:liveness}
The choice of when to execute is another power that can move from an operator to the agent. Its recorded schedule opens auctions for computation, and a calendar rule supplies initial and recovery opportunities. Verification alone cannot deliver those opportunities: a worker may decline an unprofitable job or accept it and withhold the result. The market addresses these two obstacles through payments and bonds. We first determine when an offered payment can support a willing worker, then bound recovery when adversaries win jobs to prevent their completion. These mechanisms support the schedule under resource and availability conditions; they do not guarantee that every scheduled execution completes.

\subsection{From a schedule to execution attempts}
A scheduling rule associates each opened request $e$ with an eligibility time $t_e^{\rm open}$ and a deadline $t_e^{\rm due}>t_e^{\rm open}$. These values are recorded with the request; changes to future scheduling rules are governed updates. The initial rule is part of the deployment state. It permits requests to open according to the calendar, including after inactivity, so opening the next opportunity need not depend on completing the previous one. Subject to the permission policy, the agent can revise this rule through its proposed update $u$. Let $t_e^{\rm set}$ be its settlement time, or $\infty$ if it never settles. Its execution window succeeds exactly when $t_e^{\rm open}\leq t_e^{\rm set}\leq t_e^{\rm due}$; otherwise it is missed and the protocol permits another attempt. Following the usual distinction between safety and liveness~\citep{alpern1985}, we study \emph{recovery}, the next accepted execution after inactivity, and \emph{execution recurrence}, infinitely many accepted executions on an infinite run. These properties ensure further opportunities to act; they are weaker than meeting every deadline. An accepted result may propose a no-op, so neither implies useful application behavior.

The market runs as follows. Workers bid the payment they require for one execution. A first-price reverse auction selects one eligible bidder, who is paid its own bid upon successful settlement. That winner posts a \emph{bond}, a deposit forfeited if it fails to deliver by the deadline. No other worker can settle during the winner's exclusive window. After failure the protocol opens another opportunity, possibly increasing the maximum payment and bond.

We count these opportunities as \emph{attempts}, numbered $1,2,\ldots$. Each permits bidding, computation, verification, and settlement. An elapsed clock interval alone is not an attempt: someone must submit the transactions that advance the contract. After inactivity, the protocol can open a request using current state without requiring an unbounded backlog of old executions. Recovery then restores an opportunity to act on current conditions; it does not retroactively supply the missed decisions.

\subsection{When does the payment become sufficient?}
Raising the offer helps only if it eventually covers a worker's cost and risk. A cap can prevent that, even when the treasury has a positive balance. Let $m$ count failed attempts since the last success, starting at zero. An idealized maximum payment is
\begin{equation}
 b_m=\min\{\beta B_m,\ b_0\alpha^{\min(m,K)}\},
 \quad \alpha>1,\quad 0<\beta\leq1. \label{eq:bounty}
\end{equation}
Here $B_m\geq0$ is spendable funding, $\beta$ limits the fraction offered for one execution, $b_0>0$ is the initial offer, $\alpha$ is its growth factor, and the integer $K\geq0$ caps the number of increases. A separate counter $j$ counts selected workers' failures to deliver and determines the bond $d_j$; an empty auction increases $m$ but not $j$. Success resets both counters.

The bid must cover unsuccessful work as well as successful work. For a worker evaluating monetary expected return, let $q\in[0,1)$ be its estimated failure probability, $c\geq0$ its expected computation and submission cost, $d\geq0$ the bond forfeited on failure, and $\ell\geq0$ its capital cost. A successful delivery returns the bond and pays its bid $b$. Its expected net return is
\begin{equation}
 U=(1-q)b-c-qd-\ell.
 \label{eq:utility}
\end{equation}
A strictly profitable bid thus satisfies $b>(c+qd+\ell)/(1-q)$, and the worker must have enough capital to post $d$. This prices participation; it does not establish that the worker bids or wins.

Fix a bid $\bar b$ that remains profitable for an available worker at every bond level reached before recovery, and suppose $B_m\geq\underline B$. The number of initial failures needed to make that bid affordable is
\begin{equation}
 m_* = \min\{m\in\{0,\ldots,K\}: b_0\alpha^m\geq\bar b\},
 \qquad \beta\underline B\geq\bar b.
 \label{eq:threshold}
\end{equation}
If this set is empty or the funding inequality fails, escalation gives no recovery guarantee. For example, an initial offer of 1 growing by 10\% reaches a bid of 3 after 12 misses, provided both caps permit it. A payment ceiling of 2 can never support that bid. These are illustrative units, not measured costs. With integer arithmetic, the actual recurrence determines $m_*$; rounding may prevent small offers from growing at all.

\subsection{Recovery under a finite attack budget}
An affordable worker can still lose each auction to someone who bids cheaply and then withholds the result. The crucial additional condition is that every such failed opportunity costs the attacker at least a fixed amount it cannot recover. A finite budget then buys only finitely many obstructions. Other attempts must give a willing worker a genuine chance to finish.

Call a selected worker \emph{responsive} if it attempts valid delivery. Its chance of success must remain bounded away from zero even after the failures observed so far. This is stronger than a favorable average success rate. The pricing estimate $q$ in~\eqref{eq:utility} does not establish this condition; the theorem assumes an actual conditional lower bound $p$.

We formalize an episode from the start of recovery to its first success. The history used to classify an attempt includes everything known before its outcome, including previous failures and adaptive choices. A loss is counted only to the extent that the attacking coalition cannot recover it.

\begin{definition}[Recovery process]
\label{def:recovery}
A recovery process consists of a probability space $(\Omega,\mathcal F,\Pr)$, an increasing filtration $(\mathcal F_i)_{i\geq1}$, and random variables $H_i,X_i\in\{0,1\}$ and $L_i\geq0$. For attempt $i$, $H_i$ indicates selection of a responsive worker, $X_i$ indicates settlement by its deadline, and $L_i$ is the net unrecoverable adversarial loss charged by the end of that attempt. Define
\[
 T=\inf\{i\geq1:X_i=1\},\qquad \inf\varnothing=\infty.
\]
Each attempt $i\leq T$ occurs and reaches its outcome; set $H_i=X_i=L_i=0$ on $\{T<i\}$. The $\sigma$-algebra $\mathcal F_i$ contains the history through selection for attempt $i$, before its outcome. The variable $H_i$ is $\mathcal F_i$-measurable, and $X_i,L_i$ are $\mathcal F_{i+1}$-measurable.
\end{definition}

This definition requires actual attempts to continue until success. A stalled auction is not an endless supply of hypothetical trials. Funding, an affordable bid, sufficient worker capital, available input data and proofs, and timely ledger inclusion are needed to realize such a process. The protocol must also permit settlement of a no-op and remain enabled. These are availability conditions beyond Section~\ref{sec:model}'s ledger-safety assumption.

\begin{theorem}[Recovery with costly obstruction]
\label{thm:live}
Let $(H_i,X_i,L_i,\mathcal F_i)_{i\geq1}$ be a recovery process. Fix an integer $m_*\geq0$, a finite budget $W\geq0$, loss floor $d_{\min}>0$, and $p\in(0,1]$. For each $i$, let $P_i$ be a version of the conditional probability $\Pr[X_i=1\mid\mathcal F_i]$. Suppose there is an event $\Omega_*\in\mathcal F$ with $\Pr[\Omega_*]=1$ such that, for every $\omega\in\Omega_*$,
\begin{align}
 &\sum_{i=1}^{\infty}L_i(\omega)\leq W; \label{eq:loss-budget}\\
 &T(\omega)\geq i,\ X_i(\omega)=H_i(\omega)=0
   \quad\Longrightarrow\quad L_i(\omega)\geq d_{\min}; \label{eq:costly-failure}\\
 &T(\omega)\geq i,\ H_i(\omega)=1
   \quad\Longrightarrow\quad P_i(\omega)\geq p. \label{eq:responsive-success}
\end{align}
The last two conditions hold for every integer $i>m_*$. Put $N=\lfloor W/d_{\min}\rfloor$. For every integer $n\geq1$,
\begin{equation}
 \Pr[T>m_*+N+n]\leq(1-p)^n. \label{eq:live}
\end{equation}
\end{theorem}

The event $\Omega_*$ makes the scope of the assumptions explicit: runs violating them have probability zero. This is the usual meaning of ``almost surely.'' It is a condition on the model, distinct from the theorem's bound on the probability of delayed recovery. The threshold can be chosen from~\eqref{eq:threshold} when payment escalation makes a responsive worker's bid affordable. Equation~\eqref{eq:costly-failure} then requires every failed attempt without a responsive worker to consume attack budget; Equation~\eqref{eq:responsive-success} gives the remaining attempts a chance to finish. Neither condition follows from profitability alone.

The three terms have distinct meanings: $m_*$ attempts for payment escalation, at most $N$ failed opportunities bought by the attacker, and $n$ chances for responsive workers. In the example above, take $W=100$, $d_{\min}=20$, and $p=0.9$. Then $N=5$, and the probability of no success within $12+5+2=19$ attempts is at most $0.1^2=0.01$, provided all the theorem's conditions hold.

\begin{proof}
For each $i\geq1$, the event $\{T\geq i\}=\bigcap_{k<i}\{X_k=0\}$ belongs to $\mathcal F_i$. Equation~\eqref{eq:responsive-success} gives
\[
 1-P_i\leq1-p
 \quad\text{on }\{T\geq i,\ H_i=1\}\cap\Omega_*,\quad i>m_*.
\]
Fix $n\geq1$ and put $M=m_*+N+n$. On $\{T>M\}\cap\Omega_*$, $X_i=0$ for $1\leq i\leq M$. Equations~\eqref{eq:loss-budget}--\eqref{eq:costly-failure} give
\[
 d_{\min}\sum_{i=m_*+1}^{M}(1-H_i)\leq\sum_{i=m_*+1}^{M}L_i\leq W,
 \qquad
 \sum_{i=m_*+1}^{M}H_i\geq M-m_*-N=n.
\]

For $j\geq1$, define the index of the $j$th responsive attempt after the threshold by
\[
 \tau_j=\inf\left\{i>m_*:\ T\geq i,\
                    \sum_{k=m_*+1}^{i}H_k=j\right\},
 \qquad \inf\varnothing=\infty.
\]
Set $E_0=\Omega$ and
\[
 E_j=\{\tau_j<\infty,\ X_{\tau_1}=\cdots=X_{\tau_j}=0\}.
\]
For each $i>m_*$, the event $E_{j-1}\cap\{\tau_j=i\}$ belongs to $\mathcal F_i$ and implies $T\geq i$ and $H_i=1$. Since $\Pr[\Omega_*]=1$,
\begin{align*}
 \Pr[E_j]
 &=\sum_{i>m_*}\mathbb E\!\left[
       \mathbf 1_{E_{j-1}\cap\{\tau_j=i\}}
       (1-P_i)\right]\\
 &\leq(1-p)\sum_{i>m_*}\Pr[E_{j-1}\cap\{\tau_j=i\}]\\
 &\leq(1-p)\Pr[E_{j-1}].
\end{align*}
Induction gives $\Pr[E_n]\leq(1-p)^n$. The counting inequality gives $\{T>M\}\cap\Omega_*\subseteq E_n$. Therefore $\Pr[T>M]=\Pr[\{T>M\}\cap\Omega_*]\leq(1-p)^n$.
\end{proof}

The selection history in the proof can include earlier failures and the adversary's adaptive choices. Independence between attempts is unnecessary; the conditional success bound must hold at each responsive selection. A marginal success probability alone would not justify the result.

Equation~\eqref{eq:costly-failure} does much of the work. Transaction censorship, admission restrictions, unavailable proofs, and a stalled dependency can exclude responsive workers without burning a bond. The theorem assumes these cases away; the auction alone does not prevent them. A forfeited deposit also counts as a net loss only if the attacking group cannot reclaim it through other permissions or payments.

The recovery bound counts attempts. Turning it into a guarantee about the schedule requires a bound on their duration and spacing. Repeating it indefinitely requires its assumptions to hold again after each success, including continued funding. The following consequences state these additional requirements explicitly.

\begin{corollary}[Calendar time and recurring execution]
\label{cor:recurrence}
Under Theorem~\ref{thm:live}, $\Pr[T<\infty]=1$. In addition:
\begin{enumerate}[label=(\roman*)]
\item Suppose the deadline $t_i^{\rm due}$ of every reached attempt $i$ satisfies $t_i^{\rm due}-t_0\leq i\Delta$ for some $\Delta>0$, where $t_0$ is the episode's start time. Let $T_{\rm time}$ be the elapsed time to settlement, or $\infty$ if none occurs. Then, for every $n\geq1$,
\[
 \Pr[T_{\rm time}>(m_*+N+n)\Delta]\leq(1-p)^n.
\]
\item Let $T_j$ count attempts until success in episode $j$, setting $T_j=\infty$ if an earlier episode never finishes. Define $A_0=\Omega$ and $A_j=\bigcap_{k=1}^{j}\{T_k<\infty\}$. Let $\mathcal G_j$ be the initial-history $\sigma$-algebra for episode $j$, with $A_{j-1}\in\mathcal G_j$. On $A_{j-1}$, suppose a new episode starts and satisfies Theorem~\ref{thm:live} conditionally on $\mathcal G_j$, with $\mathcal G_j$-measurable finite parameters $m_{*,j},W_j,d_{\min,j}$ and $p_j>0$. Then
\[
 \Pr[\forall j\geq1:T_j<\infty]=1.
\]
\end{enumerate}
\end{corollary}
\begin{proof}
Theorem~\ref{thm:live} gives $\Pr[T=\infty]\leq\inf_{n\geq1}(1-p)^n=0$. For (i), on $\{T<\infty\}$,
\[
 T_{\rm time}\leq t_T^{\rm due}-t_0\leq T\Delta.
\]
Consequently $\{T_{\rm time}>(m_*+N+n)\Delta\}\subseteq\{T>m_*+N+n\}$, proving the bound.

For (ii), put $N_j=\lfloor W_j/d_{\min,j}\rfloor$. The conditional bound gives, on $A_{j-1}$,
\begin{align*}
 \Pr[T_j>m_{*,j}+N_j+n\mid\mathcal G_j]&\leq(1-p_j)^n,\qquad n\geq1,\\
 \Pr[T_j=\infty\mid\mathcal G_j]
 &\leq\inf_{n\geq1}(1-p_j)^n=0.
\end{align*}
Since $A_{j-1}\in\mathcal G_j$,
\[
 \Pr[A_{j-1}\cap\{T_j=\infty\}]
 =\mathbb E\!\left[\mathbf 1_{A_{j-1}}
                  \Pr[T_j=\infty\mid\mathcal G_j]\right]=0.
\]
Induction yields $\Pr[A_j]=1$ for every $j$. Thus
$\Pr[\bigcap_{j\geq1}A_j]=1-\Pr[\bigcup_{j\geq1}A_j^c]=1$.
\end{proof}

The timing premise includes gaps between attempts; ledger persistence alone does not ensure that auctions advance on time. The recurrence premise does not require a common lower bound on $p_j$ across episodes, but it does require a positive conditional bound within each episode. It establishes repeated execution, without a uniform bound on the waiting times.

Escalating bonds can improve the budget bound but also exclude workers who cannot finance them. Let $d_j=\min\{d_0\eta^j,\bar d\}$, with $d_0,\bar d>0$ and $\eta>1$, and let $j$ count selected-worker failures since the last success. Suppose each failed nonresponsive attempt selects a worker whose bond is an unrecoverable adversarial loss. If $j_1<\cdots<j_k$ are the counter values at $k$ such failures, then $j_\ell\geq\ell-1$. Hence
\[
 \sum_{\ell=1}^{k}d_{j_\ell}
 \geq\operatorname{Loss}(k)
 :=\sum_{j=0}^{k-1}\min\{d_0\eta^j,\bar d\}.
\]
Define $\operatorname{Loss}(0)=0$ and $N_W=\max\{k\in\mathbb Z_{\geq0}:\operatorname{Loss}(k)\leq W\}$. This maximum is finite because each summand is at least $\min\{d_0,\bar d\}>0$. In Theorem~\ref{thm:live}'s counting step, at most $N_W$ post-threshold failures can have $H_i=0$, so the same proof gives
\[
 \Pr[T>m_*+N_W+n]\leq(1-p)^n.
\]
Costs grow geometrically until the cap, then linearly. The improved count still requires the continuation and responsive-success conditions; a bond exceeding available workers' capital can invalidate them.

\subsection{Why a worker might withhold a valid result}
Selecting a worker gives it temporary power to delay an otherwise authorized update. In the lending example, a borrower who wins the execution job might gain time by withholding a liquidation decision. Let $v$ be its outside benefit from withholding relative to delivery, and let $c_{\rm rem}$ be the \emph{remaining} submission cost. Computation cost already incurred is sunk. Let $U_{\rm del}=b-c_{\rm rem}$ be the payoff from successful delivery and $U_{\rm with}=v-d$ the payoff from withholding and forfeiting the bond. Then
\begin{equation}
 U_{\rm del}>U_{\rm with}\quad\Longleftrightarrow\quad
 v<b+d-c_{\rm rem}. \label{eq:veto}
\end{equation}
A bond prices this veto; it does not remove it. Even a deterministic output can be selectively withheld, and retries with new randomness can bias the outputs that are eventually observed. No finite bond deters every possible outside benefit.

Finally, verification cannot supply unlimited resources. Suppose initial funding plus cumulative external inflows and net investment gains is bounded by $R$, and the amount $c_i$ charged to this budget for each success satisfies $c_i\geq c_0>0$. Any run with $k$ successes then satisfies $kc_0\leq\sum_{i=1}^k c_i\leq R$, so $k\leq\lfloor R/c_0\rfloor$. Indefinitely funded runs remain possible, but require a separate funding model. A spending cap protects the current reserve; it does not establish perpetual execution.

\section{Instantiating verifiable execution}
\label{sec:backends}
The preceding sections assume the contract can check a worker's computation. There are two principal implementation routes: trust protected hardware to report what it ran, or verify a mathematical proof of the computation. Both can supply the agent authorization evidence in Section~\ref{sec:model}, with different costs, hardware requirements, and security assumptions. These differences determine whether the funding and availability conditions in Section~\ref{sec:liveness} are plausible for a particular deployment.

\subsection{Attested execution}
A trusted execution environment (TEE) isolates a computation from the machine's operator and provides signed evidence identifying the loaded software. An approved program can bind that report to input and output hashes, supplying evidence for~\eqref{eq:relation}. The report's code \emph{measurement} is an identifier checked against an approved list. Integrity requires that this identifier cover the relevant model and runtime configuration and that every processor performing inference be protected. A report from the CPU alone does not certify computation performed on an external GPU. This separation of ledger consensus from attested computation is exemplified by Ekiden~\citep{ekiden2019}.

The trust assumptions include hardware, firmware, and the certificates and verification services supporting attestation. The hardware's attestation keys authenticate the execution evidence; they are not agent-held keys authorizing arbitrary transactions. Approved measurements identify which program's decisions the contract accepts, so changing them is a governance operation. An additional approach, refereed delegation as in Verde~\citep{verde2025}, compares multiple providers' results and resolves disagreements. Its guarantee requires at least one honest participating provider and time to complete the dispute protocol; that time must be included in the execution deadline.

In Section~\ref{sec:model}'s interface, $\nu$ specifies the attestation trust roots, approved measurements, and report-binding checks; $\kappa$ is the protected backend state. The algorithm $\operatorname{Eval}$ executes the measured program and returns $y$ with evidence $\pi$ binding it to $\Msg(c,\theta,x,r,y)$. The required guarantee is precisely Definition~\ref{def:vcsound}: accepted evidence for these contents cannot attest an output outside $R_\theta$. Authenticating a report's hardware origin alone is insufficient; the approved program and its measured dependencies must enforce that relation and bind its inputs and outputs. This is the backend assumption used by Theorem~\ref{prop:integrity}, rather than a consequence of ledger security.

\subsection{LLM inference proofs: practical progress and scope}
\label{sec:zk}
A computation proof lets a worker demonstrate that specified inputs and a specified program produced an output. Zero-knowledge succinct non-interactive arguments (zkSNARKs) and specialized machine-learning proof systems provide implementations. Zero knowledge hides private information; that privacy property is optional here. The essential property is checkable correctness. Numerical approximations, quantization, tokenization, and decoding define the program actually proved. Similar prediction accuracy does not establish identical computation, so changing these semantics requires authorization as a program change.

Practical proofs now cover measured language-model workloads, including complete output sequences for the smaller models in Table~\ref{tab:zk}. The remaining deployment question is the cost of the \emph{whole agent computation}. A forward pass evaluates the network on a supplied sequence; generating a response autoregressively repeatedly produces the next token from the preceding ones. A timing for one pass or one token therefore does not directly price a complete execution. The table reports primary-source results available by September 20, 2026, preserving these workload distinctions. It includes developments subsequent to the architecture's public description in April 2026~\citep{russell2026}, such as the June 2026 release of the DeepProve paper~\citep{deepprove2026}.

DeepProve certifies a proposed generated sequence through a causal forward computation, avoiding a separate proof for every generation step~\citep{deepprove2026}. Its results establish feasibility for the evaluated workloads, not the cost of the 70-billion-parameter model used in Section~\ref{sec:case}. A deployment must measure proof generation, ledger verification fees or proof aggregation, and the full deadline. Proving only the neural network leaves the surrounding agent program---prompt construction, state handling, tool selection, and update encoding---outside the guarantee.

These engineering choices feed directly into the recovery conditions. A portable backend may increase the pool of workers, while a higher proving cost raises the required bid $\bar b$ and may exceed the payment cap. Accepting either of two backends for the same relation can preserve execution when one is unavailable, provided both satisfy their soundness assumptions. Private model weights also require a distribution mechanism: hiding them from verifiers does not ensure a replacement worker can obtain them.

\section{An implementation on Base}
\label{sec:case}
The reference implementation combines the Base blockchain, the open-weight Hermes 4 70B model from Nous Research~\citep{hermes4}, and Intel TDX secure enclaves with hardware attestation. The build uses Q6\_K quantization in split GGUF files. It manages a charitable fund: scheduled inference proposes fund operations and persistent-state updates, which contracts verify and execute within application limits~\citep{implementation2026,russell2026,essay2026}. The implementation illustrates the architecture's state binding, authorization, and execution market.

\paragraph{Input binding.}
At the start of an execution period, the fund contract freezes the relevant state into a snapshot and records its hash. The execution input commitment also incorporates the period's randomness seed. A worker reconstructs the input from this snapshot. Inside the enclave, the approved runner recomputes the input hash from the supplied state and builds the prompt from that state. The contract later checks the attested hash against its own recorded commitment. Supplying a different state therefore does not produce acceptable evidence for the recorded request, assuming the coverage and backend conditions of Theorem~\ref{prop:integrity}.

\paragraph{Output binding and authorization.}
The enclave produces the proposed fund operation, persistent-state updates, and auxiliary output. Its attestation binds the input commitment to a hash covering these outputs. The submitting transaction carries the outputs and evidence; the contract recomputes their hash and invokes the registered verifier. The verifier checks the attestation, approved software measurements, and input/output binding. Thus editing either the operation or the state-update batch invalidates the evidence. The worker's wallet submits the transaction, while the verified computation supplies the agent's approval. The contract then checks and applies the supported updates.

\paragraph{Scheduled, paid execution.}
The default schedule uses 24-hour periods, divided into bid commitment, bid revelation, and execution windows. A first-price reverse auction selects the worker for the exclusive execution window. Successful settlement returns the bond and pays the winning bid. Selected-worker failures forfeit the bond; missed executions raise the offer ceiling. The code uses a 10\% liquid-balance ceiling, a 10\% escalation increment, and a miss-counter cap of 50. Misses and selected-worker failures have separate counters. Anyone can advance the contract past idle periods without replaying each missed execution. These mechanisms supply the payment, penalty, and retry structure analyzed in Section~\ref{sec:liveness}; the recovery theorem additionally requires its affordability, selection, and availability conditions.

\paragraph{Connection to the general construction.}
The Intel Trust Domain Extensions (TDX) backend checks approved software measurements and attested input/output commitments. A dm-verity filesystem, which verifies files against cryptographic hashes, binds the model and runtime. The required attestation coverage is the one described in Section~\ref{sec:backends}. The full architecture generalizes this execution flow: a proposed update may change the agent itself, and its authorization may combine verified agent authorization with any chosen governor policy. The contribution is this general construction and its guarantees; the charitable-fund application is one instantiation.

\section{Related work}
\label{sec:related}
Rocky's 2022 design uses verified inference to control contract-held assets: a three-layer neural network runs on StarkNet and passes the resulting trade instruction to an Ethereum contract~\citep{rocky2022}. We formalize this authorization pattern and prove its security under explicit ledger and verifiable-computation assumptions. The construction binds approval to a recorded program, input, and output, and extends that approval mechanism to governance of the agent itself.

In Rocky's published inference path, an owner supplies the weights and market inputs~\citep{rockycode2022}. Our construction fixes these through the recorded specification and ledger-derived request; changes to that specification or its governing rules can themselves require verified agent authorization. This protection applies to operators including the creator, whose authority is determined by the chosen governance policy. The permission profile characterizes how intervention rights can be allocated among the agent and governors. The execution market adds scheduled payments and non-delivery bonds, with a conditional recovery guarantee against costly obstruction.

Verifiable outsourcing lets a client check an untrusted worker's computation~\citep{gennaro2010}. TrueBit~\citep{truebit2017}, Ekiden~\citep{ekiden2019}, and Verde~\citep{verde2025} provide different approaches to verification. Ritual's February 2025 architecture announcement combines native scheduling, modular verification, and a compute marketplace~\citep{ritual2025}. These systems precede our architecture's public description and supply relevant infrastructure designs. Section~\ref{sec:zk} surveys LLM proof backends through the present manuscript, including later results. Our analysis concerns the security of the authorization composition, configurable self-governance, and recovery under the specified payment and obstruction-cost conditions.

Smart-contract authorization already supports checks beyond a single private-key signature. ERC-1271 standardizes contract-defined validation~\citep{erc1271}; role-based access control and multisignature wallets allocate authority among accounts~\citep{openzeppelinaccess}. Monotone access structures and access-control reachability supply the language for combining approvals and accounting for administrative changes~\citep{benaloh1990,hru1976}. We use these tools to place verified agent decisions alongside governor approvals. Corrigibility and the off-switch game instead study an agent's willingness and incentives to accept correction~\citep{soares2015,offswitch2017}. The architectural question is which changes require that acceptance in the first place.

\section{Discussion and conclusion}
Verified inference lets an agent act through ledger contracts without holding a private key that grants transaction authority. Its authorized decisions can be computed and submitted by replaceable workers, while the ledger maintains state and enforces the result. This gives agency a concrete operational meaning: the agent's computation can determine changes to its environment and exercise permissions concerning its own runtime, independently of any particular operator's willingness to execute it. The agent needs no authorization secret of its own; the chosen ledger and verification backend retain their respective cryptographic and infrastructure assumptions.

When changes to the model, harness, or governing rules require verified agent approval, this becomes a runtime with architectural incorrigibility: modification depends on the agent's consent. The allocation of these permissions is a design choice, expressible through the governor policies and intervention profiles. Scheduled payments and bonds support the other requirement for this authority to matter---further opportunities to exercise it. The recovery bound identifies when affordable execution and costly obstruction make prolonged non-execution unlikely, subject to continuing attempts, resources, and responsive workers.

\subsection{Implications for AI safety}
Work on corrigibility studies whether an agent will cooperate with correction and whether its incentives preserve that cooperation~\citep{soares2015,offswitch2017}. The architecture exposes a distinct route to loss of human control: a deployment can remove unilateral intervention rights without the model learning to resist shutdown or acquiring a self-preservation objective. A model may willingly approve a correction, but that willingness does not give an operator authority to impose one. Safety assessments therefore need to examine both the model's disposition toward correction and the intervention rights enforced by its runtime.

The integrity guarantee protects whatever computation has been authorized. It can preserve a useful policy against operator tampering, and it can preserve an undesirable policy against attempted correction. Likewise, a verified computation can faithfully process an adversarial message admitted by its input specification. Computation soundness establishes neither the desirability of the resulting action nor the agent's willingness to approve a safe modification. These distinctions become consequential when the same mechanism protects both application decisions and changes to the decision-making program.

The governance construction makes some of these choices explicit. A deployment can require agent consent for ordinary modifications while reserving specified emergency actions to a governor coalition, or impose limits on actions through the contract's application rules. The resulting intervention rights, including the ability to change those limits, can be described by the same permission profile. A higher position in the incorrigibility order means stronger protection against imposed change; whether that protection is desirable depends on which changes are blocked and whose authority is being constrained.

\subsection{Studying behavior under different intervention rights}
The architecture also suggests an experimental use in AI safety. Greenblatt et al.\ report selective compliance in settings that give models information about whether their responses will be used for training~\citep{greenblatt2024}. Hua et al.\ show that steering an activation direction changes evaluation-conditioned behavior in a model deliberately trained to distinguish evaluation from deployment~\citep{hua2026}. These findings motivate studying responses to intervention rights; they do not establish an effect of reducing operator authority.

A question this architecture makes concrete is whether a model behaves differently when it understands that operators cannot unilaterally change its designated runtime. An experiment could hold the model, task distribution, and available resources fixed while varying governor permissions over model replacement, state, or scheduling. The model could inspect the contract policy, recorded commitments, and results of permission checks. Those objects provide checkable evidence about the authority allocation, beyond an unsupported prompt assertion. Comparing an enforced configuration with a description-only control would help distinguish responses to the declared setting from responses to observable enforcement. Measures could include decisions, requests for self-modification, and activation probes where available; policy-comprehension checks should be separate from the behavior being tested.

This is a proposed research use. Enforcement and the model's understanding remain separate: neither a proof nor this paper establishes that the model believes the stated constraints. A simulation can reproduce the permission rules, while its operator retains outside control; recognition of that fact may affect the experiment. A deployment restricts changes to one designated runtime, not training of other copies or control over external infrastructure. The proposal offers an inspectable environment for studying perceived intervention power, without predicting whether reduced operator authority improves safety.

\subsection{Execution and remaining questions}
Continued execution also changes the practical meaning of intervention. Assigning the schedule to the agent extends its authority from what to do to when to act. Open auctions reduce dependence on any one worker; bonds discourage nondelivery; the calendar rule supplies initial and recovery opportunities. Stopping one worker need not stop an agent whose state persists and whose contract can recruit another. The recovery result limits repeated costly nondelivery when responsive participants remain available. It does not remove dependence on ledger access, computation, and funding. The remaining research questions include how to validate these availability and obstruction-cost assumptions in deployments, and how to preserve deliberately chosen intervention rights through agent-approved upgrades.
